## 計画からの乖離(裁定の差分)

計画末尾の指示「乖離する裁定をしたときは doc/log の新しいエントリに差分を記録する」に基づく一覧。

1. **明示的 eff 注釈の開放**(§7.6 への追加裁定):
   `@ Print` / `@ {A, B}` のようなラベル付き閉行注釈は、**本体検査では Rigid 尾部・
   公開スキーマでは Generic 尾部**として開く。`@ {}` は閉じたまま(純粋)。
   閉じたままだと sample.kel:357(println を handle の下で呼ぶ)が型付かない。
   Rigid 尾部なので「本体が注釈に無いエフェクトを起こす」ことは引き続き拒否される。
2. **Apply の軽い双方向化**(§7.3 への追加): 関数型を先に分解し、引数(特にラムダ)を
   期待型で検査する。引数ラムダの行が本体の perform 解決(D22)より先に確定するために必須
   (sample.kel:416-418 の with_file + with 糖衣が要求)。
3. **D22 の非修飾解決の絞り込みを「行の最左(=最内ハンドラ)優先」に精密化**。
   計画の「明示ラベルにあるものを優先」だけでは copy(:418)の write が
   File と Console の両方に該当して曖昧になる。最左優先は Scoped Labels の
   最左一致・実行時の最内捕捉と一致する。
4. **組み込み/プレリュードと同名のユーザ宣言は「照合の上で受理」**(§7.4 の運用具体化):
   sample.kel 自身が Unit / List / Console / Add / Add[Int32] / Never 等の
   プレリュード相当を宣言するため。実体は組み込み側を使い、ユーザ vs ユーザの重複は
   従来どおりコヒーレンス違反で拒否する。
5. **module 平坦化(D21)を M10 から M9 に前倒し**: module Parser を参照する parens が
   sample.kel §9 の途中にあり、M9 の完了条件(§9-§10 の型検査)がこれを要求した。
   実装は改名 + 同義語表(非修飾名 → 修飾名)。コンパニオン型規則(:581)も同じ表で通る。
   **未対応**: module 内 let の相互参照(sample.kel は使っていない)、module の入れ子、
   非コンパニオン内部型の同義語が外にも見えること、pub の可視性検査(§2.1 どおり延期)。
6. **テスト機構は cram 一本**(§9.1-9.2 の (rule (diff)) + run_tests.ml を置き換え):
   dune promote の運用は同じで追加コードがゼロ。`.t` ファイルへの追記だけでケースが増える。
7. **パターン束縛の match 脱糖はパーサでなく elab 側**(§6.4 の1行の変更):
   トップレベルの `let (a, b) = ...` は式に脱糖できないため、elab が単一ケース match と
   同じ扱い(単相束縛 + 網羅性キュー)で両方の位置を一本化した。
8. **resume は値(VResume)ではなく env 経由**(§8.2 の変更): second-class(D19)を
   実装レベルでも強制する。値表現に VResume は存在しない。
9. **空の match 本体を文法で許可**: `n match {}`(Never の節ゼロ網羅)。あわせて
   Maranget の complete 判定を「シグネチャが Some [] なら roots が空でも網羅」に修正
   (MiniLang:1721 の roots.nonEmpty 条件は Never の節ゼロで誤って非網羅になる)。
10. **menhir --strict の投入は M2 でなく M3 開始時**(§3.2 の1マイルストーンずれ):
    M2 時点では文法が無く、未使用トークン警告がエラー化するため。
11. **数値パターンの重複検出は値正規化**(0x1 と 1 を同一視)。計画に記述が無かった点の裁定。
12. **クラスメソッド名の値環境登録は非修飾+修飾の両方**。メソッド参照 `map` / `Functor.map`
    の両方が引ける(§7.4 の「両方」を環境レベルで実装)。
    (260829-4 B4 追記: 非修飾名の所有者は高々 1 クラスであることを elab が保証する。
    同名メソッドを持つ 2 クラスは宣言時に拒否 — 保証が無いと elab と interp が
    別のインスタンスを選ぶコヒーレンス破れになることが実測された。)

## 立案後の敵対的検証(260829-2b)で見つけた欠陥と修正

計画完遂後、3レンズ(健全性/仕様適合/頑健性)の敵対的検証を実機で回し、実行実証された
欠陥を修正した。以下はすべて再現 .kel を実行して確認済み。

### 健全性(修正済み)
1. **行変数 [R] が行位置で使えない**: rewrite_row が行変数のカインドを `vkind = KRow` の
   構造マッチで見ていたため、arity 0 の型パラメータ(make_rigids が new_kind_var()、
   行位置で KVar{→KRow})を取りこぼし、sample.kel:136-138 の `fst({x=1, _item="hi"})` や
   :144-150 の `describe(#Other)` が落ちていた。→ `same_kind` で判定。
2. **注釈付き非値が値制限を迂回**: `gen = ... || annotated || ...` が注釈付き非値
   (`let slot: Ref[h,T] = Ref.new(...)`)を一般化し、run の Rigid h が Generic に漏れ、
   リージョンから可変参照を持ち出せた。→ `gen = is_fun || is_value` に。
3. **前方参照シグネチャの省略 @ 過剰一般化**: 注釈内の省略 @ が独立な行変数を生み、
   前方参照された関数が過剰に一般化され、宣言順でエフェクト検査が抜けた。
   → 全矢印に @ 明示された注釈だけを前方参照に使う。
4. **型クラスディスパッチが誤った引数で選ぶ**: `(Int32, A) => Int32` の第1引数 Int32 で
   誤ディスパッチ。→ メソッドスキーマから「パラメータが頭に現れる引数位置」だけで
   ディスパッチ。宣言時制約も「引数の頭に現れること」に強化(List[A] は宣言拒否)。
5. **組み込みインスタンスの実行時差し替え**: `type instance Add[Int32]` 再宣言で
   `2 + 3` が -1 に。→ 組み込みキーと同じ (cls,con) は実体を差し替えない。
6. **module 内 instance が実行時に見つからない**: interp が同義語表を引かず。
   → `Decls.resolve_con` を通す(sample.kel §13 の BigInt が実行可能に)。
7. **組み込み型名の newtype 再宣言**: `newtype Boolean = Yes` が新データ型として通り、
   網羅性と組み込みインスタンスが破綻。→ 予約型名テーブルで再宣言拒否。
8. **extern の再宣言**: `extern "prim" let __int32_add(x: String,...)` で嘘の型。
   → extern 登録簿で再宣言拒否。
9. **let rec の非関数右辺**: 型検査を通って実行時に必ず落ちた。→ elab で拒否。

### 頑健性(修正済み — 終了コード規約に整形)
存在しないファイル(exit 64)、不正 UTF-8(exit 2)、巨大接尾辞幅、module の入れ子/
module 内 effect・式(flatten の Type_error を捕捉、exit 1)、handle の未知エフェクト修飾
(Option.get 前に実在検査)、Out_of_memory(exit 3)、Stack_overflow(exit 3)、
cancel ログの生 OCaml 例外表現。

  変更しない。
