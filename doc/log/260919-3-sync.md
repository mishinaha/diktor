## 4. 親リポジトリ(keleut)への申し送り(残るもの)

### 4.1 計画 §14 の P32〜P36

- **P32(予約語の一覧)**: 仕様に予約語の一覧が無い。`{run: () => Unit}` が書けないのは矢印ではなく
  `run` が予約語だからで、`{run: Int32}` も同じ位置で落ちる。diktor の予約語は `_` を除いて 25 語で、
  レコードのラベル・コンストラクタのフィールド名・セレクタのいずれにも使えない。一覧を §0 に足すか、
  ラベルの位置だけ予約語を通すかを決めてほしい。後者を採るなら、パンニング `{run}` は `run h { … }` と
  衝突するので除外する必要がある。
- **P33(非修飾の組み込み値の予約)**: `par` / `par_map` / `pinned` と型クラスのメソッドの非修飾名は
  トップレベルの `let` が黙って覆える(台帳 V23)。予約すると D43「値は大域先勝ち」の見直しになり、
  `let show` や `let add` を書けなくする影響が大きいので、本計画では修飾名だけを守った。仕様として
  認めるか、名前を予約するかを決めてほしい。
- **P34(`pub let rec` の値束縛)**: `pub let rec` の値束縛(関数型の注釈を持つ `let rec k: (Int32) => Int32 = …`)に
  `pub_pure_rows` の経路を入れていない。群が共有の行を持つ設計と噛み合わないためで、仕様が
  `let rec` の値束縛を認める形を書いていないので先回りしなかった。認めるなら diktor 側の規模は S である。
- **P35(操作型の頭の `@`)**: effect の操作型の頭の矢印に書いた `@` は受理されるが、`perform` も
  `handle` も操作スキーマの行を捨てるので型付けに効かない。仕様には事実として書き(`:483-485`)、
  diktor は現状(受理して捨てる)を観測点に固定した — `annot_rows.t` の ophead(`effect Weird = { op: () => Unit @ {Print} }`
  が exit 0)と ophead2(頭の `@` に未知のラベルを書くと `ophead2.kel:1:41` で落ちる)である。
  書けなくするか、§14 の TODO(操作型が周囲の行を参照できる仕組み)で意味を与えるかを、その TODO と
  一緒に裁定してほしい。拒否するなら「`@ {}` だけは許すか」も決める必要がある。
- **P36(標準ライブラリ所有インスタンスの再宣言)**: プレリュードが `Show[List[_]]` / `Show[Option[_]]` を
  持つので、ユーザが同じ頭を書き直す形はコヒーレンス違反になる。型・エフェクト・型クラスの再宣言(D35)と
  同じく「標準ライブラリと同じ頭は受理し、実体は標準ライブラリ側を使う」例外を認めるかを決めてほしい。
  diktor の現状の観測点は `classes.t` の pshowdup(同梱プレリュードの下でユーザが `Show[List[_]]` を
  宣言すると「インスタンス Show[List] が二重に宣言されています(コヒーレンス違反)」)と pshow2 群
  (`--no-prelude` で `newtype List` から自分で書けば通る)である。受理するなら「無視する」のではなく
  「ユーザ側を採らない」ことを仕様に書く必要がある(台帳 V38 の診断も相手を名乗るべきになる)。

### 4.2 本計画の実施で新しく立ったもの(P37〜P46)

P37〜P40 は M29 / M30 の実測と台帳から、P41〜P46 は M32 の事前検証が反証の過程で残した事実から立てた。
P41 以降は本エントリの執筆時に `_build/default/bin/main.exe`(diktor df441e4)へ最小入力を食わせて

- **P37(型クラスのパラメータの穴の個数)**: 仕様 `:344` は「Type か、HKT の `F[_]` のように Type を取って
  Type を返す形に限る」と書き、M32 が実測に合わせて「穴は `F[_, _]` と複数でもよい」を括弧で足した。
  diktor は `type class C2[F[_, _]]` も `type class C3[F[_, _, _]]` も受理し、インスタンス宣言とメソッド
  解決まで通る。穴の個数に上限を置くかを決めてほしい。

  `--type-check` に掛けると exit 0。
- **P38(組み込みの型クラスの再宣言と D35 の照合)**: 組み込みの `Show` をユーザが再宣言するとき、
  D35 の照合はメソッドの型の書き方に敏感で、エイリアス経由の型では落ちて矢印リテラルなら通る。
  仕様が求めるのは型の一致か、字面の一致かを決めてほしい。I.6 の前後で挙動は変わっておらず、
  M30 の変更が原因ではない。

  「type class Show の宣言が組み込みの宣言と一致しません(メソッド show の型が違います)」で exit 1。
  `type class Show[A] { val show: (A) => String }` は exit 0。
- **P39(`type class` の経路と組み込みの修飾名)**: D141 の保護は `flatten_modules` の `module` 宣言の
  経路に乗るので、`type class` の経路は組み込みの修飾名をいまも覆える(台帳 V35)。D141 の原文は
  「ユーザの `module` 宣言で同じ綴りを作れない」と宣言形を名指ししており、射程を宣言形で切るか、
  値環境の綴りで切るかを決めてほしい。P33 と同じ回で問うのが筋である。
  再現: `type class Ref[A] { val new: (A) => Int32 }` を書くと `Ref.new(1)` がそのメソッドに解決され、
  「Int32 は Ref のインスタンスではありません」になる(組み込みの `Ref.new` へ届かない)。
- **P40(差し替えプレリュードの信頼境界)**: `--prelude` で差し替えたプレリュードを信頼境界の内側と
  するかを決めてほしい。いまは平坦化時の検査と型検査時の検査で扱いが割れており(台帳 V36)、
  差し替えプレリュードもユーザのプログラムと同じに組み込みの修飾名を奪えない。

  与えると `visbipre.kel:1:14` で「module Ref の new は組み込みの Ref.new と同名です」で落ちる。
- **P41(改行が宣言を終える規則の明文)**: 仕様が書いているのはトップレベルのセミコロン省略だけで、
  改行が宣言を終える一般規則の明文が無い。宣言の頭と本体の `{` の間に改行を置くと落ちるのは
  前提つきインスタンスに限らず、前提なしのインスタンスでも `type class` でも同じである。M32 が

  書かれていない。改訂前からの穴である。

  §9 の表の括弧書きではなく §14 の TODO として書く場所を決めてほしい。

  関数束縛の `let idf(x) = x` は `idf : (A) => A` と一般化される。
- **P43(型エイリアス経由の入れ子の矢印の `@`)**: `pub` の完全注釈の要求(`:789-791`)が型エイリアス
