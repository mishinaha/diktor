## 2. 実装記録・計画の誤り訂正

- **A10**: exhaust.ml §10.3 の旧主張「整数の正規化は往復するので健全です」は
  **偽**だった(OCaml native int は 63 ビットで `0x7FFFFFFFFFFFFFFF` が
  ラップし、到達可能な節に偽の到達不能警告が出た)。M12(A3/A10)で
  Int64 全域の正規化に修正し本文も改稿済み。本エントリで訂正として記録。
- **乖離 9 の残り**: 260829-2 乖離 9 の「MiniLang:1727 の roots.nonEmpty」は
  MiniLang:1721 が正(260829-3 で訂正済み)。同型の判定は :1706 / :1756 に
  もある。M19(G3a)で判定は sig_complete に一本化された。
- **I3「最左 = 最内」**: elab §11.20 の旧正当化「行の最左 = 最内ハンドラ」は
  一般には偽。行が handle の入れ子から**推論で**組み立てられる限りは正しい
  (§11.24 が TRowExtend(label, …, outer) で積むため)が、注釈が行を明示的に
  書いたときの最左は**書かれた順序**であって入れ子順ではない(E1/E2 の
  反例を実測 — h2 が内側でも {E1, E2} 注釈の op は E1 に解決される)。
  静的解決と実行時捕捉は食い違わない(perform は解決済みの完全名 oid を
  運ぶ)ので挙動は健全、誤っていたのは説明。M20 で本文改稿。
- **計画の D23 の言い回し**: 計画 §3 の裁定原文は Ord[Float64] を「半順序」と
  書いたが、NaN は自分自身とも比較不能(le(nan, nan) = false)なので
  **反射律が成り立たず、半順序ですらない**。M12 の実施記録の言い回し
  (「半順序ですらない」)が正。builtin.ml §13.4 の本文は M12 改稿時から
  正しい。
- **V5(--prelude の信頼境界)**: `--prelude PATH` は任意ファイルを
  プレリュード扱いにでき、プレリュード保護(D35 の構造照合や extern 登録簿)
  をユーザ自身が差し替えの中で書き換えられる。これは**仕様**とする —
  --prelude は「自分の処理系に与える標準ライブラリの差し替え」であり
  信頼境界の内側。保護が守るのは「プログラムがプレリュードを黙って
  上書きする」事故であって、「利用者が意図してプレリュードを差し替える」
  行為ではない。

## 3. 親リポジトリ(keleut)への提案(§15 の一覧 + M11〜M19 検証での追加)

そのまま issue に貼れる本文は計画 §11「裁定の原文」にある。ここでは一覧と、
検証で増えた追補を記録する。

計画 §15 の 9 系統(要旨):

1. **Array のシグネチャ**(D64)— Array / MutArray 分離を推奨。bump / leak の
   再現は test/spec_gaps.t に固定済み。M20 検証で動機が 2 つ増えた:
   (a) @ {} コールバックが共有 Array を破壊でき par の決定性が破れる、
   (b) pub の「@ 省略 = 純粋」も同じ経路で破れる。Array.each に Heap を
   課す弥縫(I12)は行共有ゆえ成立しないことを実測で確認し撤回済み —
   分離だけが読みの純粋性を正しく表せる。
2. **`@ 行` 注釈の意味論**(D44)— 「下界」裁定。字義だと sample.kel 自身が
   型付かない実測付き。effect 宣言の操作型を対象外にすべきこと。
3. **非修飾操作名の解決規則**(D22 の規則文化)— perform は「行の最左」、
   handle は「被覆が一意」。「最内ハンドラ」と書くと嘘(上記 §2 の I3)。
4. **Console のハンドル禁止の明文化**(D63)— M20 で diktor 側は禁止を実装。
5. **§14 TODO への暫定裁定の確認**(D65)— §1 の表。
6. **pub の `@` 省略**(D44 の pub 面)— 「本体は純粋・公開スキーマは行多相」。
7. **cancel 節の再入の意味論**(D66 / I10)— 3 案比較。現状(再入を許し
   Unwind は抑制)は test/spec_gaps.t に固定。
8. **{base with} の基底制限**(D67)— 字句規則の帰結の明文化。
9. **追補** — Ord の NaN 意味論(半順序ですらない点も含めて)、浮動小数
   リテラル字句、Show[Float64] の非有限値、スーパークラス構文、前提つき
   インスタンス構文、非 pub newtype のコンストラクタ可視性、module 入れ子。

M11〜M19 の検証で増えた追補:

10. **高階位置の省略 `@` の意味論**(V14)— newtype フィールドや effect
    操作型の中の矢印の省略 `@` は Generic に一般化され、構築側と消費側が
    別々にインスタンス化するため、エフェクトつきの閉包を「純粋」として
    取り出せる(@ {} も pub の純粋性も par の決定性も破れる)。省略 `@` の
    意味(sample.kel:315-316)を高階位置について規定してほしい。候補:
    (a) 宣言の型パラメータで束縛することを要求、(b) 高階位置の省略は
    `@ {}`、(c) 現状(多相)を明文化して決定性保証の但し書きにする。
11. **ファイル prim の行**(V15)— `__open` / `__read` / `__write` /
    `__close` が行なしで型付けされており、@ {} コールバックからファイル
    I/O ができる。File プリム層の設計(行を持つか、with_file 専用に隠すか)
    の裁定が要る。行を与えると sample.kel の with_file の形(構造照合)と
    衝突し得る。
12. **BOM / CR 改行**(M18 検証)— 先頭 U+FEFF をスキップするか、CR のみの
    改行を改行と数えるか、いずれも仕様に記述が無い。
13. **末尾カンマの境界**(D56 の精密化)— 末尾カンマが付くのは最後の
    **要素**の後だけで、`...rest` / `extends T` の終端子の後には付かない。
    仕様 §1 の明文化候補。
14. **節パターンの型注釈**(D57 の帰結)— 将来 `case p: T =>` を導入する
    なら型注釈内の矢印に括弧を必須とする(字句層は型の終わりを決められない)。

## 4. 計画 §2.3 との差分の棚卸し(D3)

v0 で実働まで入っている**(unify §8.7。Functor[List[_]] と sample.kel §8 の

クラス)のみが v1 に残る。260829-2 の「意図して残した v1 / 延期項目」の

要る」は実現不能な前提。M17 は同じ型の多相 let で代用してゴールデン化
